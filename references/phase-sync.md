# Phase 13: Sync — モデル⇔実装の差異解消

## 目的

`--analyze` は差異を **指摘するだけ** で止まる。`sync` はその先 — 発見したモデルと実装の差異を
**判定 → 計画 → 承認 → 実装 → モデル再整合** まで進め、ドメインモデルとコードを継続的に一致させる。

「モデルが先か、コードが先か」を毎回ユーザーと決めながら、差異を1件ずつ台帳で潰していくフェーズ。

## 中心原則

1. **差異は双方向**。「コードを直す」だけでなく「モデルを直す」も一級の解決策。どちらが正かは差異ごとに判定する。
2. **矛盾は黙って呑まない**。コードを読んだ結果、ユーザーの前提（モデル）が崩れる発見をしたら、
   並べ替え・実装を進める前に必ず提示して合意を取る。
3. **承認ゲート**。アーキテクチャ分岐・破壊的操作・複数の妥当な方針があるときは、実装前に選択肢を提示して選ばせる。
4. **正直な報告**。テストの失敗・スキップ・スコープ外は明記する。「通った」は実際に緑を確認してから言う。
5. **モデル⇔コードを離さない**。コード変更で差異が閉じたら、対応する `docs/domain/*.md` の赤付箋・未解決の問いを
   その場で「解消」に更新する。片方だけ直して放置しない。

## 進行手順

### Step 1: 差異を収集する

差異の出どころ:
- 直近までの各フェーズの `--analyze` で挙がった「ギャップ・違反・命名ズレ」。
- `docs/domain/*.md` の赤付箋（🔴）・「未解決の問い」・「フィードバック」節。
- `.ddd-session.json` の `openQuestions` / `divergences`。

各差異を1行に正規化して台帳の素案にする。粗くてよい。まず全部出す。

### Step 2: 差異ごとに「権威 (authority)」を判定する

ユーザーに問う:「この差異、**正しいのはモデルですか、コードですか**？」

| 権威 | 意味 | 解決アクション |
|------|------|----------------|
| **model** | モデルが正・実装が追いついていない | コードを直す（Step 3 以降） |
| **code** | 実装が正・モデルが古い/誤り | `docs/domain` を直す（モデル更新のみ） |
| **収束 (converge)** | 両方が歩み寄る（用語統一・概念分割など） | モデルとコードの両方を直す |

種別 (type) も付ける: `gap`（未実装）/ `mismatch`（食い違い）/ `naming`（命名衝突）/ `violation`（DDD 原則違反）。

> ⚠️ コードを読んで初めて分かる事実（例:「依存がクリーンに成立しない」）は、権威判定の前に提示する。
> ユーザーの当初仮説が変わることがある。

### Step 3: 実装計画を立てる（model / 収束 権威のコード修正分）

`code` 権威（モデル更新のみ）の差異は Step 6 へ。コードを直す差異は計画を書く:

- **目標**: 何をどう変えると差異が閉じるか（変更後の振る舞い・データフロー）。
- **影響ファイル**: 変更/新規/テストを列挙。
- **リスク**: 変更で新たに生じる副作用（今回の例: パイプライン再配置で diff にノイズが乗る等）。
- **方針分岐**: 妥当な選択肢が複数あるなら案を並べ、トレードオフとコストを示す。
- **スコープ外**: 今回やらないこと＝新たな赤付箋として残すもの。
- **フェーズ分割**: 低リスクなリファクタ → 中核変更 → テスト → ドキュメントの順。

### Step 4: 承認を取る

スコープ・方針分岐をユーザーに提示して選ばせる（選択肢形式が望ましい）。
承認なしにアーキ変更・破壊的操作を実装しない。

### Step 5: 実装する

- **TDD を基本**: 期待挙動のテストを先に書ける場合は先に。最低限、変更後にテスト/lint/build を実走する。
- プロジェクトのテスト規約・ツール（`vitest` / `tsc` / `eslint` など）に従う。
- 後方互換を壊さない（opt-in 化・デフォルト挙動維持）。
- 秘密情報・破壊的操作のガードを既存実装に合わせる。
- 結果（パス数・失敗・スキップ）を正直に報告する。

### Step 6: モデルを再整合する

- コード変更で閉じた差異 → `docs/domain/*.md` の該当赤付箋を「解消（どう実装したか）」に更新。
- `code` 権威の差異 → モデル文書側を実装に合わせて精緻化。
- `収束` の差異 → 用語・構造を両側で揃える（例: glossary に反映）。
- 残ったスコープ外は新しい赤付箋／未解決の問いとして明記。

### Step 7: 台帳に記録する → 成果物 `sync.md`

差異ごとに状態を更新。`pending → planned → in-progress → done`（または `model-updated` / `deferred`）。

### Step 8: コミット（ユーザー依頼時のみ）

- **依頼があったときだけ** コミットする。
- デフォルトブランチ上なら **先にブランチを切る**。
- 論理単位で分割（feat / refactor / docs）。コミット規約はプロジェクトに従う。

## 他フェーズ／`--analyze` との連携

- どのフェーズの `--analyze` の最後でも、差異が出たら「`/ddd sync` で計画・実装まで進められます」と誘導する。
- `sync` 自体も `--analyze` の延長として、複数フェーズにまたがる差異をまとめて扱える。
- 実装中にモデルの抜け（集約・イベント・用語の不足）が見つかったら、`workflows` フェーズ同様
  該当フェーズへの出戻りを提案し、勝手に塗りつぶさない。

## Session State 拡張

`.ddd-session.json` に差異台帳を構造化して持つ:

```json
{
  "currentPhase": "sync",
  "divergences": [
    {
      "id": 1,
      "fromPhase": "storming",
      "type": "gap",
      "authority": "model",
      "decision": "run --explore で配線 (2パスクロール)",
      "status": "done",
      "commit": "2773a1f"
    }
  ]
}
```
